# Estate atlas

What the lab runs, at the same detail level the public repos already publish.
(Deeper operational specifics live in each owning repo and in the
[incident register](https://github.com/lentago/.github/blob/main/fleet-reports/incidents.md),
which deliberately publishes post-mortems verbatim.)

## Two estates, one operating model

**The homelab** — a multi-node Proxmox VE cluster with a NAS, running (among
other guests) a production Home Assistant OS VM, an observability shipper LXC,
a small always-on web server, a LAN GitHub Actions runner, and the five-worker
Claude agent fleet ("the bullpen"). Every VM and LXC on the cluster is declared
in Terraform and applied on merge.

**The cloud** — a three-tier AWS environment (multi-AZ VPC, ECS Fargate behind
an ALB, RDS Postgres, ElastiCache, WAF, KMS, budgets), 100% Terraform, serving
four live public sites and a serverless Ask endpoint.

The operating model is identical on both: everything is code, every change is
a pull request, merges apply automatically, humans own every merge.

## Which repo moves which surface

| Merge to `main` in… | …moves this live surface |
|---|---|
| [solidago](https://github.com/lentago/solidago) | The AWS platform (plan-on-PR, apply-on-merge via OIDC) |
| [kalmia](https://github.com/lentago/kalmia) | Every Proxmox VM/LXC (applied by the LAN self-hosted runner) |
| [claytonia](https://github.com/lentago/claytonia) | The agent-runner pool itself, plus worker tooling via a 5-minute GitOps pull |
| [drosera](https://github.com/lentago/drosera) | Grafana Cloud dashboards, alert rules, and the central Alloy config |
| [betula](https://github.com/lentago/betula) | Log collectors (Firewalla/Zeek → Loki; AWS → Axiom) |
| [homeassistant-config](https://github.com/lentago/homeassistant-config) | The running smart home (5-minute GitOps poller, validate-then-reload with auto-rollback) |
| site repos ([lentago.dev](https://github.com/lentago/site-lentago-dev), [icecreamtofightwith.com](https://github.com/lentago/site-icecreamtofightwith-com), [pondviewlane.com](https://github.com/lentago/site-pondviewlane-com)) | The live sites (build + deploy onto solidago's platform) |
| [.github](https://github.com/lentago/.github) | Org and repo settings — rulesets, required checks, labels, repo existence — via fleet settings-as-code |

Two deliberate exceptions prove the rules: [brasenia](https://github.com/lentago/brasenia)
(the wall display) has **no** apply-on-merge of its own — its runtime is
provisioned from kalmia — and **myosotis** (the private agent-context ledger)
has no PR flow at all: a single writer appends, humans only read. Its pattern
is documented publicly in
[claytonia → docs/context-ledger.md](https://github.com/lentago/claytonia/blob/main/docs/context-ledger.md).

## Where the telemetry lives

- **Grafana Cloud** (Mimir + Loki, free tier) — dashboards and alerting, fully
  Terraform-provisioned from [drosera](https://github.com/lentago/drosera);
  per-host Alloy agents push metrics and logs.
- **Axiom** — full-volume log capture and long-retention archive, shipped by
  [betula](https://github.com/lentago/betula)'s collectors.
- **Weekly fleet report + incident register** — published in
  [.github/fleet-reports](https://github.com/lentago/.github/tree/main/fleet-reports),
  regenerated by CI from the repos themselves.

## The agent layer

The [claytonia](https://github.com/lentago/claytonia) bullpen: five headless
Claude Code workers on the LAN sharing a NAS drop-folder queue. Any trigger
that can write a file can dispatch work; an idle worker claims the job
atomically, works in a clean checkout, and opens a PR. Workers **never merge**
— the GitHub App they authenticate as cannot — and each job emits per-run
metrics to Grafana. The `@claude` responder (from
[shared-workflows](https://github.com/lentago/shared-workflows)) is the
browser-side of the same idea: mention it on any issue or PR.
